ERP Seem Semrac · Feuille de route

Reprendre le contrôle en 8 semaines

Rendre l'ERP maintenable par un prestataire extérieur sans jamais perdre le contrôle, sûr en cybersécurité, automatisable, déployable en Docker — et te rendre autonome sur la base de données et les imports. Chaque semaine se termine par un livrable concret.

7 juillet → 4 septembre 2026 7 objectifs + 1 transverse 1 thème / semaine Cap : « opérationnel et sûr », pas « parfait »
Principe directeur — autonomie + propriété.

Un prestataire peut travailler sur l'application, mais rien de vital ne doit dépendre de lui. Le code, les comptes, les secrets, les sauvegardes et la connaissance restent chez toi. Le prestataire est un exécutant remplaçable, pas un point de défaillance.

Objectif transverse · Priorité absolue

Les sauvegardes — la mesure n°1, non négociable

Avec l'auto-hébergement, plus personne ne sauvegarde à ta place : le cloud Supabase le faisait, ton serveur ne le fera pas tout seul. C'est la seule protection contre une panne serveur, un ransomware, une erreur du prestataire ou une fausse manipulation. Sans backup, tout le reste est secondaire.

Quotidienne & automatiquepg_dump du conteneur PostgreSQL + copie du bucket Storage (documents/plans GED).
≥ 2 emplacementsDont un hors du serveur (autre disque, stockage objet chiffré, hors-ligne) — sinon un serveur perdu = tout perdu.
Restauration testéeAu moins une fois. Une sauvegarde jamais testée ne compte pas.
ChiffréeElles contiennent des données RH et compta (données personnelles).
AutomatiséePar N8N (workflow n°1) dès qu'il tourne ; en attendant, un simple cron + pg_dump sur le serveur.

→ À mettre en place la semaine même où la base est auto-hébergée (S3/S4), voire un pg_dump cron dès le premier jour de mise en ligne.

Sécurité du code & cybersécurité opérationnelle

S2 · S4 · S8

Déjà fait

  • Audit adversarial : 15/16 défauts corrigés
  • RBAC fermé par défaut
  • Signataires fiables (PIN/session)
  • Anti-abus formulaire public
  • Harnais anti-régression

À faire (S2) — de « bêta assumée » à « production sûre »

  • Sortir les secrets du code : JWT secret et bootstrap ADMIN/246810 → variables d'environnement (.env hors Git), secret JWT régénéré, PIN admin changé
  • Clés Supabase : ton instance génère ses nouvelles clés ; la clé anon committée (cloud) devient caduque ; la clé service_role reste strictement côté serveur
  • RLS table par table — priorité aux données RH (pointages, salariés) et compta (RGPD)
  • Anti-flood / rate-limit via reverse-proxy ou pare-feu applicatif (Crowdsec, fail2ban) sur /api/login et /api/contact — à configurer en S4
  • Sauvegardes automatiques — mesure n°1 (voir bandeau rouge)
  • RGPD : registre des traitements, durées de conservation, information des salariés (pointages = sensibles)
  • Journalisation des connexions et actions sensibles (déjà partielle via les historiques)

Tu dois maîtriser

Lire les alertes du Security Advisor de Supabase, distinguer une clé secrète d'une clé publique, et vérifier que les sauvegardes tournent.

Fin S8 (optionnel, recommandé) : pentest léger par un prestataire spécialisé une fois le durcissement fait → attestation de sécurité.

Automatiser avec N8N

S7 – S8

À faire — approche

N8N = outil visuel (boîtes reliées par des flèches) pour automatiser les tâches répétitives, auto-hébergé chez toi dans Docker — cohérent avec la propriété (obj. 2 et 7).

  • Installer N8N dans le même Docker que l'app
  • Le connecter à Supabase (lecture/écriture via l'API)
  • Brancher les workflows par ordre de valeur (catalogue complet en annexe A)

Les 3 premiers workflows (plus fort impact)

  • 1. Sauvegarde quotidienne de la base (aussi un point cybersécurité)
  • 2. Alertes d'échéances sécurité — VGP, DUER, contrôles réglementaires à terme
  • 3. Relance des factures impayées — email automatique à J+30, J+45

Tu dois maîtriser

Créer un workflow simple (déclencheur → action), le tester, le mettre en pause. On en construit 1 ensemble, tu refais les suivants seul.

S6

À faire — méthode

7

Docker — auto-hébergement complet (Supabase + app)

S3 – S4

Le choix retenu

Tout auto-héberger sur ton propre serveur — la base Supabase ET l'application, en Docker. Plus de dépendance à Cloudflare ni au cloud Supabase : les données et l'infrastructure sont 100 % à toi.

Un seul docker-compose.yml :

  • Stack Supabase : PostgreSQL (la vraie base), PostgREST (l'API), GoTrue (auth), Storage (bucket GED), Studio (l'admin), Kong (passerelle) — compose officiel prêt à l'emploi
  • L'app ERP (Hono en conteneur Node)
  • N8N (automatisations)
  • Reverse-proxy (Caddy ou Traefik) : HTTPS automatique + routage
La contrepartie, en toute honnêteté : ce que le cloud faisait pour toi (sauvegardes, mises à jour de sécurité, dispo 24/7) devient ta responsabilité. Gérable, mais ça impose de la rigueur : sauvegardes testées, mises à jour, surveillance. C'est le prix de la maîtrise totale.

Étapes

  • S3 — En local d'abord : compose officiel Supabase, générer tes propres secrets (JWT, mots de passe Postgres, clés anon/service), Dockerfile de l'app, adapter src/db.ts, recréer le schéma (scripts_import/*.sql)
  • S4 — Migrer + produire :
    1. Export de la base cloud (pg_dump) → fichier .sql
    2. Import chez toi (psql < dump.sql) ; vérifier les compteurs de lignes table par table
    3. VPS (OVH / Scaleway / Hetzner) ou serveur interne, au nom de l'entreprise, SSH par clé
    4. docker compose up -d, domaine + HTTPS, checklist post-déploiement, Studio verrouillé derrière un mot de passe fort (accès total à la base)

Tu dois maîtriser

docker compose up -d / down / logs / ps, savoir où est le .env (tes secrets) et ne jamais le committer. Comprendre que Studio auto-hébergé = le dashboard Supabase, mais chez toi.

📄 docs/technique/12-docker-installation.md — installer toute la stack de zéro sur un serveur vierge. Le docker-compose.yml + .env.example versionnés = la preuve ultime de réversibilité : n'importe qui remonte tout en une commande.

05

Annexes B & C — Garde-fous

la checklist import et les clauses du contrat

Annexe B

Checklist « import de données sans fuite »

  • Le fichier CSV ne contient que les colonnes de la table cible
  • Aucune donnée réelle sensible collée dans un chat, une IA, un email
  • L'import se fait depuis ton poste vers ta base, sans intermédiaire
  • Le PAT et les clés secrètes jamais partagés ni écrits dans un fichier suivi par Git
  • Après import : vérifier le nombre de lignes + 2–3 lignes au hasard
  • Supprimer les fichiers temporaires (CSV, exports) après usage
  • En cas d'erreur : savoir annuler (supprimer les lignes importées par un critère commun)
Annexe C

Clauses non négociables du contrat de maintenance

  1. Propriété intellectuelle — le code et les données appartiennent à l'entreprise à 100 %, y compris les développements du prestataire
  2. Réversibilité — à chaque fin de mission : remise du code, de la doc à jour et des accès ; changement de prestataire sans blocage
  3. Comptes & secrets — hébergés par l'entreprise ; le prestataire a des accès nominatifs révocables, jamais la propriété
  4. Confidentialité / RGPD — protection des données (surtout RH) ; interdiction de copier les données hors de l'environnement
  5. Délais d'intervention (SLA) — temps de réponse en cas de panne bloquante
  6. Traçabilité — toute modification passe par le dépôt Git (pas de correctif « en direct » non tracé) et met à jour le CHANGELOG
